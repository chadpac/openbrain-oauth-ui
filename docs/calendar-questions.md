# Read-only Calendar questions

This extends Ask Open Brain with a per-question Calendar control. It does not
create, edit, reschedule, or delete Google events, and uses the existing two
read-only Google OAuth scopes.

## Use

1. Open Ask Open Brain.
2. Check **Check my Google Calendar for this question**, or choose a Calendar
   example, which fills the input and checks the control without sending yet.
3. Ask a complete question, for example:
   - What is on my calendar tomorrow?
   - Am I free Thursday from 1 to 4 pm?
   - What is on my calendar next week?
4. Send. The control immediately resets to off. The response shows the exact
   window, timezone, and sources used, with a **Calendar check · not saved** note.

The Calendar mode supports schedule listings and availability checks for the
signed-in user's selected Google calendars and visible Open Brain family events.
It cannot check other members' private Google connections or perform writes.
Use a complete date/time question each time: prior Calendar messages are excluded
from subsequent requests. General assistant features work as before with the
Calendar control off. Morning means 8 am–noon, afternoon noon–5 pm, and evening
5–10 pm; explicit times are preferable for exact availability.

## Privacy and authorization

The mode is opt-in for each request. Automatic daily/weekly AI briefings do not
opt in. The server accepts only the literal boolean `use_google_calendar: true`.

The existing user authentication and household-membership checks run first.
The planning model receives only the typed question, server-provided household
local date/time, timezone, and interpretation instructions. It receives no event
records, previous Calendar answers, Health records, or general app context.

After validating the interpreted window, the server calls the existing
`google-calendar-oauth` events action with the requesting user's bearer token.
That function continues checking the authenticated user's own connection and
selected calendar IDs. Request-supplied owner IDs are ignored. Family events are
read with the user-scoped Supabase client, household filter, and existing RLS.

The final answer is calculated directly from event intervals, not generated by
the AI model. It contains no proposed actions. Calendar questions and answers
are held only in the current page's chat state, excluded from sessionStorage and
later AI requests. Server-side history handling also removes messages marked
`source: google_calendar`. Responses use Cache-Control: no-store. Reloading or
clearing chat removes the transient Calendar messages.

Health tracking tables are never queried by the Calendar route. Calendar events
can themselves contain sensitive titles; fetched titles are never sent to the
planning model. Information a user types directly into their question still goes
to the existing AI provider for date/time interpretation, as described in the
privacy policy.

## Availability rules

- Overlapping busy intervals are merged. Open intervals are calculated from the
  union, avoiding double-counting events visible in more than one source.
- Google events marked transparent/free, or declined on that calendar, do
  not block time. Tentative/non-declined events conservatively block time.
- All-day Google dates float on their stated dates, with exclusive end dates.
  The read window is padded around full local days to catch these records when
  a selected calendar has a different timezone. Results are filtered to the exact
  requested window before answering.
- Family all-day datetime inputs are normalized to whole local days. A final
  non-midnight datetime includes that day; a midnight end is exclusive.
- Missing/invalid end times do not produce a false free/busy claim. An unknown
  family-event end matters on its start day; the response requests correction
  instead of claiming availability. Invalid or ambiguous DST clock times require
  clarification. Times use the household timezone, not the browser or server's.
- Empty selection, disconnection, API failure, partial source reads, and oversized
  result sets never produce an all-clear response.
- Windows are limited to 31 local days within the past week and next 60 days.
  Listings show at most 30 events; availability calculates from up to 1,000 Google
  and 250 family records. Over-limit reads request a narrower window.

The result covers only the stated sources, not every possible real-world
commitment. Natural-language interpretation can choose the wrong window; every
answer displays the interpreted dates/times so the user can check it.

## Deployment and checks

No schema change, new credentials, or additional Google scopes are needed.
Deploy `google-calendar-oauth` first for its new `busy` flag, then
`open-brain-assistant` including `calendar-questions.ts` and `deno.json`. Retain
`verify_jwt = false` for the Google callback function and `true` for the assistant.
Publish the dashboard, About/Privacy copy, and PWA v18 through the existing
repository hosting flow. An updated browser with an old assistant fails closed
instead of presenting a general AI answer as a Calendar result.

```sh
node --test tests/calendar-questions.test.cjs tests/google-calendar.test.cjs
python tests/browser-calendar-questions.py
python tests/browser-calendar.py
```

Node 24+ and Python Playwright Chromium are used. Tests use synthetic users,
mocked AI/Calendar responses, and no live calendar contents. A signed-in live
acceptance check still needs the user: opt in, ask about tomorrow and an explicit
availability window, compare with Google, then send a normal question and verify
Calendar mode reset. Test a transparent all-day event and an event with no end
time. The Google reader and assistant can be rolled back to their previous
versions; no token or schema changes need reversal.
